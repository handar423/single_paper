\section{\sysname Design}

\sysname employs a two-level hierarchical orchestration approach for 
serverless function and request: complementary swarming request routing at the 
inter-node level and monotonic scale-up request scheduling at the intra-node level.

\subsection{Complementary Swarming Request Routing}
\label{sec:design:placement}

The complementary swarming routing algorithm addresses the inter-node resource fragmentation 
posed by heterogeneous function resource demands, as quantified in 
\S\ref{sec:background:demand-analysis}. It pursues a dual objective: i) maximizing 
cluster-wide resource utilization by co-locating functions with complementary CPU 
and memory profiles on the same node, thereby mitigating resource stranding; 
and ii) enhancing instance reuse by deliberately narrowing the set of distinct 
functions served per node. To achieve this, the algorithm proceeds iteratively. 
In each round, it assigns the workload of a function to one or more worker nodes 
based on the function's resource profile and, when necessary, logically swaps partial
assignments of other already-placed functions to improve complementary packing. 
For functions requiring distribution across multiple nodes, the algorithm performs 
fine-grained load splitting according to the function resource demand distribution. 
The algorithm outcome is a stable request-to-node mapping that balances complementary 
packing with demand-aware load~distribution.

\subsubsection{Modeling Node Capacity and Function Demand}
\label{subsec:modeling}

A precise formulation of the routing problem requires clear representations of 
both node resource capacity and function resource demand.

\textbf{Node Resource Capacity.} We model a worker node $N_j$'s resource capacity 
as a two-dimensional vector $\mathbf{C}_j = \left(C_j^{\text{cpu}}, C_j^{\text{mem}}\right)$, 
representing its CPU cores and memory (in GB). Similarly, we denote by 
$\mathbf{C}_j^{\text{idle}} = \left(C_j^{idle,cpu}, C_j^{idle,mem}\right)$ the 
vector of idle resources on $N_j$ at any given moment. 
For simplicity, we focus on CPU and memory as the primary bottleneck resources. 
Our algorithm can be extended to incorporate other resources (\emph{e.g.}, network bandwidth) by expanding the resource vector. 
We define the \textbf{overall resource utilization} of a node \(N_j\) as the sum of its CPU and memory utilization:
\[
U(N_j) = \frac{C_j^{\text{cpu}} - C_j^{idle,cpu}}{C_j^{\text{cpu}}} + \frac{C_j^{\text{mem}} - C_j^{idle,mem}}{C_j^{\text{mem}}}
\]
Here, we simply sum CPU and memory utilization because function demands will be standardized to eliminate weight differences between resources. An optimization step is considered beneficial if it increases \(U(N_j)\).

\textbf{Function Resource Demand.} Modeling the resource demand of a function is 
more nuanced. We characterize it along three orthogonal dimensions:

\begin{enumerate}
    \item \textbf{Demand Ratio ($r_i$)}: The intrinsic CPU-to-memory ratio required 
    by a single execution of function $F_i$. The value of $r_i$ quantitatively 
    indicates a function's resource affinity: a relatively small $r_i$ signifies 
    memory-intensive behavior, whereas a relatively large $r_i$ corresponds to 
    compute-intensive behavior. To reduce problem complexity, we assume this 
    ratio remains invariant across requests of the same function. This assumption
    is consistent with the stable CPU-to-memory profiles observed in Figure~\ref{fig:ratio_stability_scatter}. 
    We discuss
    the single-resource-dominant exceptions and the scope of this model in
    \S\ref{sec:discussion}.

    \item \textbf{Demand Volume ($\mathbf{V}_i$)}: The aggregate resource demand 
    vector for function $F_i$ within the scheduling window, denoted as 
    $\mathbf{V}_i = \left(V_i^{\text{cpu}}, V_i^{\text{mem}}\right)$. Here, $V_i^{\text{cpu}}$ and 
    $V_i^{\text{mem}}$ represent the predicted total CPU (\emph{e.g.}, in core-seconds) 
    and memory (\emph{e.g.}, in GB-seconds) required to process all expected 
    requests of $F_i$ in that window, respectively. While the accurate 
    prediction of $V_i$ is orthogonal to our placement algorithm (and its accuracy 
    naturally affects overall performance), our design accepts such a predicted 
    vector as input.

    \item \textbf{Demand Distribution ($D_i$)}: The statistical distribution of 
    per-request resource requirements, derived from historical traces. $D_i$ is 
    crucial for fine-grained load splitting when a function must be spread across 
    multiple nodes.
\end{enumerate}
Together, the tuple $\left<r_i, \mathbf{V}_i, D_i\right>$ forms a comprehensive 
demand profile for each function $F_i$, enabling our algorithm to reason about 
complementary routing and proportional workload distribution simultaneously.

% \setlength{\belowdisplayskip}{-140pt}
\begin{algorithm}[t]
    \caption{\mbox{Complementary swarming routing.}}
    \noindent \textbf{Data:}
    \begin{algorithmic}[1]
    \Statex \begin{itemize}
        \setlength{\itemindent}{.0em} % 控制缩进
        \item Pending assignment vector \(\mathbf{R} \in [0,1]^n\).
        \item Assignment matrix \(\mathbf{L} \in [0,1]^{m \times n}\).
    \end{itemize}
    \Require $ $
    \Statex \begin{itemize}
        \setlength{\itemindent}{.0em} % 控制缩进
        \item Node set \(\mathcal{N} = \{N_1, \dots, N_m\}\).
        \item Function set \(\mathcal{F} = \{F_1, \dots, F_n\}\).
    \end{itemize}
    \Ensure Optimized routing map $\mathcal{P}: \mathcal{F} \times [0,1] \to \mathcal{N}$.
    
    \State \textbf{// Step 1: Initialize state \& normalize function demands}
    \State \(\mathbf{L} \gets \mathbf{0}_{m \times n}\), \(\mathbf{R} \gets \mathbf{1}_n\)
    \For{$F_i \in \mathcal{F}$}
        \State $\mathbf{V}_i \gets \mathbf{V}_i \times \frac{\sum_{j=1}^{m} \mathbf{C}_j}{\sum_{i=1}^{n} \mathbf{V}_i}$ \Comment{Scale demand proportionally}
    \EndFor
    \State
    
    \State \textbf{// Step 2: Main optimization loop}
    \While{$\exists \; F_i \text{ s.t. } R[i] > 0$} \Comment{Incomplete mapping}
        \State $F_a \gets \text{RandomChoice}(\{F_i \mid R[i] > 0\})$ 
        \For{$N_j \in \mathcal{N}$}
            \State \textbf{// Assignment via free capacity}
            \State $\alpha_j^{\text{free}} \gets min(\frac{C_j^{\text{idle,cpu}}}{V_i^{\text{cpu}}}, \frac{C_j^{\text{idle,mem}}}{V_i^{\text{mem}}})$
            \State \textbf{// Assignment via beneficial swaps}
            \State $(\alpha_j^{\text{swap}},\; \mathcal{S}_j) \gets \text{SwapCapacity}(F_a, N_j, \mathbf{L}, \mathbf{C}_j^{idle})$
            \Comment{$\mathcal{S}_j$: internal swap list of $(F_k, \beta_k)$}
            \State $\alpha_j^{\text{max}} \gets min(\alpha_j^{\text{free}} + \alpha_j^{\text{swap}}, R[a])$
            \State $\Delta U_j \gets \text{UtilGain}(F_a, \alpha_j^{\text{max}}, \mathcal{S}_j, \mathbf{C}_j)$
        \EndFor

        \State \textbf{// Decision \& Assignment (ignoring edge cases)}
        \For{$N_j \in \mathcal{N}$, \textbf{descending} order of $\Delta U$}
            \If{$R[a] \leq 0$} \textbf{break} \EndIf
            \State $L[j, a] \gets L[j, a] + \alpha_j^{\text{max}}$, $R[a] \gets R[a] - \alpha_j^{\text{max}}$
            \For{$(F_k, \beta_k)$ in $\mathcal{S}_j$}
                \State $L[j, k] \gets L[j, k] - \beta_k$, $R[k] \gets R[k] + \beta_k$
            \EndFor
        \EndFor
    \EndWhile
    \State

    \State \textbf{// Step 3: Generate $\mathcal{P}$ from $L$}
    \For{$F_i \in \mathcal{F}$}
        \State $p_{\text{start}} \gets 0.0$ \Comment To store workload percentile range
        \For{$N_j \in \mathcal{N}$, where $L[j,i] > 0$, in random order}
            \State // We use half-open intervals $[p_s, p_e)$, except the last interval which is closed at $1$.
            \State $\mathcal{P}(F_i, [p_{\text{start}}, p_{\text{start}} + L[j,i])) \gets N_j$ 
            \State $p_{\text{start}} \gets p_{\text{start}} + L[j,i]$
        \EndFor
    \EndFor
    \State \Return $\mathcal{P}$


\end{algorithmic}
\label{alg:placement}
\end{algorithm}
}

\subsubsection{Complementary Swarming Routing Algorithm}
\label{subsec:placement-algorithm}

\looseness=-1
Algorithm~\ref{alg:placement} presents the complementary swarming routing 
workflow. It takes as input the set of nodes $\mathcal{N}$ with their capacity 
vectors $\mathbf{C}_j$, and the set of functions $\mathcal{F}$ with their demand 
profiles $\langle r_i, \mathbf{V}_i, D_i \rangle$. The algorithm outputs a routing 
map $\mathcal{P}: \mathcal{F} \times [0,1] \to \mathcal{N}$. This mapping 
determines the request routing rule: when the workload of function $F_i$ is split 
across multiple nodes, $\mathcal{P}$ assigns each request from $F_i$ to a specific 
node based on the request's percentile in the function demand distribution $D_i$. 
This percentile-based splitting is illustrated in Figure \ref{fig:placement_p}.

  \vspace{-10pt}
  \caption{Generate $\mathcal{P}$ from $L$.}
  \vspace{-10pt}
  \label{fig:placement_p}
\end{figure}
}

\textbf{Step 1: Initialization \& Demand Normalization.}
The algorithm maintains two key data structures initialized in this step: i) a 
pending assignment vector $\mathbf{R}$, where $R[i]$ denotes the fraction of 
$F_i$ demand yet to be assigned, initialized to $1$ for all functions; and ii) an 
assignment matrix $\mathbf{L}$, where $L[j,i]$ records the fraction of $F_i$ 
demand currently assigned to node $N_j$, initialized to all zeros (line~2). 
Furthermore, we scale the demand vector $\mathbf{V}_i$ of each function 
proportionally so that the aggregate demand matches the total cluster capacity 
($\sum_i \mathbf{V}_i = \sum_j \mathbf{C}_j$). This normalization ensures the 
subsequent routing operates under a balanced supply-demand premise~(Line~3--4). 

\textbf{Step 2: Iterative Optimization Loop.}
The core of the algorithm is an iterative loop that runs until all function demands 
are placed ($R[i]=0, \forall i$, Line~7). In each iteration, it randomly selects 
a function $F_a$ with pending demand ($R[a] > 0$, Line~8). For each node $N_j$, 
the algorithm evaluates two ways to accommodate $F_a$: i) using the idle node 
resources, which yields a capacity $\alpha_j^{\text{free}}$ computed as the 
minimum ratio of idle CPU/memory to $F_a$ demand (Line~11); and ii) through 
beneficial swaps, where the subroutine $\text{SwapCapacity}$ logically replaces
fractions of existing assignments to host as much of $F_a$ demand as possible,
provided that doing so improves the node utilization $U_j$ (Line~13, detailed 
in Algorithm~\ref{alg:swap-capacity}). $\text{SwapCapacity}$ returns both the 
maximum $F_a$ demand fraction $\alpha_j^{\text{swap}}$ that can be hosted by 
function swapping, and an internal swap list $\mathcal{S}_j$ containing pairs
$(F_k,\beta_k)$, where $\beta_k$ is the fraction of $F_k$ demand swapped out of
$N_j$. These swaps only modify the assignment matrix during plan computation;
they do not directly trigger runtime pod migration or eviction. The total accommodation capacity for $F_a$ on 
$N_j$ is then $\alpha_j^{\text{max}} = \min(\alpha_j^{\text{free}}+\alpha_j^{\text{swap}}, R[a])$~(Line~14).

After evaluating all nodes, the algorithm sorts them in descending order of the 
utilization gain $\Delta U_j$ (Line~17) and assigns $F_a$ pending demand greedily. 
For each node in this order, it assigns up to $\alpha_j^{\text{max}}$ of $F_a$ demand, 
updates $\mathbf{L}$ and $\mathbf{R}$ (Line~19), and simultaneously processes 
the internal swaps in $\mathcal{S}_j$: for each function $F_k$ in $\mathcal{S}_j$, 
the algorithm reduces the swapped fraction $\beta_k$ in $\mathbf{L}[j, k]$ and 
adds $\beta_k$ back to $F_k$ pending demand $\mathbf{R}[k]$ (Line~21). This process 
continues until $F_a$ demand is fully assigned ($R[a]=0$). Because the total 
function demand was scaled to match the total cluster capacity in Step 1, it is 
guaranteed that $F_a$ demand can eventually be fully accommodated, and the loop 
will not terminate with $R[a] > 0$. To ensure the loop convergence speed, the 
algorithm skips nodes whose utilization gain $\Delta U_j$ is below a predefined 
empirical threshold (\emph{e.g.}, 1\%).

\textbf{Step 3: Fine-Grained Routing Plan Generation.}
After the assignment matrix $\mathbf{L}$ is determined, the algorithm converts 
the proportional assignments into a precise routing map $\mathcal{P}$ 
(Line~24--29). This process is illustrated in Figure~\ref{fig:placement_p}. 
For each function $F_i$, the algorithm sequentially allocates contiguous percentile 
intervals in $[0, 1]$ to each node $N_j$ that hosts $F_i$ (left side of the figure). 
The length of the interval assigned to $N_j$ is exactly $L[j,i]$. This completes 
the construction of $\mathcal{P}$, which is the algorithm's final output. In 
practice, to avoid resource fragmentation that could arise if certain nodes only 
receive large requests, the intervals are assigned to nodes in a randomized order 
rather than a fixed sequence; the figure omits this step for simplicity.

\parabf{Request Routing.} At runtime, the interval $[0, 1]$ is concretely mapped 
to the resource-demand percentiles of $F_i$'s requests (right side of 
Figure~\ref{fig:placement_p}). Specifically, using $F_i$'s historical demand 
distribution $D_i$, we pre-compute the resource-demand boundaries that correspond 
to each percentile sub-interval. When a new request arrives, its actual resource 
demand (derived from input parameters and data size) is located on $D_i$ to obtain 
its percentile $p$. The request is then routed to the node $N_j$ for which 
$\mathcal{P}(F_i, p) = N_j$. For example, the newly arrived request marked in 
the figure, whose demand percentile falls inside $[0.8, 1]$, would be routed 
to Node C. Our experiments obtain accurate demand estimates from the benchmark's 
known input characteristics; the algorithm can be coupled with more sophisticated 
prediction methods for further performance gains.

\begin{algorithm}[t]
\caption{SwapCapacity: Compute beneficial swap capacity}
\label{alg:swap-capacity}
\begin{algorithmic}[1]
\Require $ $
\Statex \begin{itemize}
    \setlength{\itemindent}{.0em} % 控制缩进
    \item Node $N_j$ with idle resource vector $\mathbf{C}_j^{\text{idle}}$
    \item Target function $F_a$
    \item Allocation matrix $\mathbf{L}$
\end{itemize}
\Ensure Swap capacity $\alpha^{\text{swap}}$, internal swap list $\mathcal{S} = [ (F_k, \beta_k) ]$
\State $\alpha^{\text{swap}} \gets 0$, $\mathcal{S} \gets [\,]$, $\{F_k\} \gets \{F_k | L[j, k] > 0\}$
\If{$C_j^{\text{idle,cpu}} > 0$} \Comment Determine dominant idle resource
    \State // Replace more memory-intensive first
    \State sort $\{F_k\}$ by $r_k$ \textbf{ascending} ; $\text{sign} \gets +1$
\Else \Comment{ $C_j^{\text{idle,mem}} > 0$ }
    \State // Replace more compute-intensive first
    \State sort $\{F_k\}$ by $r_k$ \textbf{descending}; $\text{sign} \gets -1$
\EndIf
\For{each $F_k$ in the sorted order}
    \If{$\text{sign} \cdot (r_a - r_k) \leq 0$} 
        \State \textbf{continue} \Comment{Swap would not improve $U(N_j)$}
    \EndIf
    \State Compute max $\beta_k$ s.t. swapping out $\beta_k$ of $F_k$ respects $\mathbf{C}_j^{\text{idle}}$
    \State $\beta_k \gets \min(\beta_k,\; L[j, k])$
    \State $\gamma_k \gets \beta_k \cdot (\mathbf{V}_k \oslash \mathbf{V}_a)$ 
        \Comment{$\gamma_k = \beta_k \cdot \min\left(\frac{V_k^{\text{cpu}}}{V_a^{\text{cpu}}}, \frac{V_k^{\text{mem}}}{V_a^{\text{mem}}}\right)$}
    \If{$\alpha^{\text{swap}} + \gamma_k > R[a]$}
        \State $\gamma_k \gets R[a] - \alpha^{\text{swap}}$; adjust $\beta_k$ proportionally
    \EndIf
    \State $\alpha^{\text{swap}} \gets \alpha^{\text{swap}} + \gamma_k$
    \State $\mathcal{S} \gets \mathcal{S} \;\cup\; \{ (F_k, \beta_k) \}$
    \If{$\alpha^{\text{swap}} \geq R[a]$} \textbf{break} \EndIf
\EndFor
\State \Return $(\alpha^{\text{swap}},\; \mathcal{S})$
\end{algorithmic}
\end{algorithm}

\parabf{Assignment via beneficial swaps.}
The SwapCapacity subroutine (Algorithm~\ref{alg:swap-capacity}) computes the
maximum fraction $\alpha_j^{\text{swap}}$ of target function $F_a$ that node
$N_j$ can host by beneficially swapping existing assignments. A swap is
beneficial only if it increases $U(N_j)$ by consuming the dominant idle
resource: when CPU is idle, $F_a$ replaces more memory-intensive functions;
when memory is idle, it replaces more compute-intensive ones. The subroutine
returns the admissible capacity $\alpha^{\text{swap}}$ and internal swap list
$\mathcal{S}$.

The subroutine proceeds in four logical steps. First, it identifies the dominant
idle resource\textemdash CPU or memory\textemdash because only one resource dimension may
remain idle after using the node's free capacity in
Algorithm~\ref{alg:placement} (lines~2--7).
Accordingly, SwapCapacity sorts assigned functions by resource-demand ratio
$r_k$: ascending when CPU is idle and descending when memory is idle, allowing
the algorithm to swap the most complementary candidates first.

\looseness=-1
Second, the algorithm performs a benefit test for each candidate function $F_k$ in the sorted list (line~9). The condition $\operatorname{sign}\cdot(r_a-r_k) > 0$ 
guarantees that swapping a fraction of $F_k$ for $F_a$ will actually increase 
$U(N_j)$. For example, if CPU is idle ($\operatorname{sign}=+1$), we must have
$r_a > r_k$, meaning $F_a$ is more compute-intensive than $F_k$ and will better 
utilize the spare CPU.

Third, for a candidate that passes the test, the algorithm computes the fraction
$\beta_k$ of $F_k$ that can be swapped out without exceeding the node's idle
resources, and limits it by the amount currently assigned to $N_j$ ($L[j,k]$)
(lines~11--12). It then translates the released capacity into an equivalent
amount of $F_a$ using $\gamma_k = \beta_k \cdot \min\left(\frac{V_k^{\text{cpu}}}{V_a^{\text{cpu}}}, \frac{V_k^{\text{mem}}}{V_a^{\text{mem}}}\right)$
(line~13), ensuring that neither CPU nor memory exceeds the released capacity.

Finally, the algorithm accumulates $\gamma_k$ until $F_a$'s pending demand is
exhausted or no beneficial candidate remains, then returns $\alpha^{\text{swap}}$
and $\mathcal{S}$ to the main loop (lines~14--17).

\parabf{Low Overhead via Partial Updates.} To keep the scheduling overhead low, 
the routing algorithm employs an incremental (partial) update mechanism. Rather 
than recomputing the full routing plan from scratch for every scheduling window, the 
system periodically monitors the latest 
demand profiles $\langle r_i, \mathbf{V}_i, D_i \rangle$ of all functions. For 
a function whose aggregate demand $\mathbf{V}_i$ has not increased and demand 
distribution $D_i$ remains statistically stable, the algorithm preserves its 
current placement. Only functions with significantly changed demand (increased 
$\mathbf{V}_i$ or altered $D_i$) are fed into the complementary swarming algorithm 
to update their assignments. This partial update drastically reduces the number 
of functions that need to be re-routed in each iteration, thereby reducing
plan-level demand relocation and the resulting instance churn while preserving
warm states. Furthermore, to prevent sub-optimality from multiple incremental
updates, the system performs a global routing-plan recomputation every 10 minutes,
recomputing all function assignments from a clean state to ensure long-term
placement quality.

\subsection{Monotonic Scale-up Request Scheduling}
\label{sec:design:scheduling}

{
\begin{figure}[t]
  \centering
  \includegraphics[width=0.8\linewidth]{figures/design/scheduling.pdf}
  \vspace{-10pt}
  \caption{Monotonic scale-up scheduling workflow.}
  \vspace{-15pt}
  \label{fig:scheduler-arch}
\end{figure}
}

The monotonic scale-up scheduler runs on each worker node. Its primary objective 
is to handle the intra-function demand variability identified in 
\S\ref{sec:background:demand-analysis} by leveraging in-place vertical scaling, 
thereby avoiding costly cold starts while maintaining high resource efficiency.

\subsubsection{Scheduler Architecture}

As illustrated in Figure~\ref{fig:scheduler-arch}, the core scheduling structure 
is organized per function. For each function $F_i$, the scheduler maintains two 
monotonic request queues: a current queue and a backup queue. Requests in both queues 
are ordered by their predicted resource demand in increasing order. This monotonic 
ordering is the key to enabling efficient in-place scaling: when an instance processes 
requests sequentially from a single queue, its resource allocation can be increased 
incrementally without~restarts.

\parabf{Request-insertion rule.} When a new request of $F_i$ arrives, its predicted 
resource demand is compared with the demand of the head (smallest) request in the 
current queue. If the new demand is smaller, the request is placed into the 
backup queue; otherwise, it is inserted into the current queue (preserving the 
monotonic order). The purpose of this rule is not merely to keep each queue sorted, 
but to guarantee that an instance, while processing requests from a single current 
queue, encounters a resource demand sequence that is monotonically non-decreasing. 
This property is essential: if an instance were forced to run a larger request before 
a smaller one, it would either have to start at the higher capacity (wasting 
resources) or be restarted after a down-scale (incurring cold-start overhead). 
The backup queue holds smaller requests until the current queue is processed,
after which the queues swap roles.

\parabf{Instance execution and priority-based selection.} A function may have from 
zero to multiple concurrent warm instances, each dedicated to fetching requests only 
from that function's current queue. The scheduler assigns a dynamic priority to 
each function (detailed in \S\ref{subsec:priority-design}). At every scheduling 
point\textemdash triggered by a new request arrival or a request completion\textemdash the scheduler selects 
the function with the highest priority and attempts to process the head request of 
its current~queue.

\parabf{Resource-assignment policy.} To execute the selected request, the scheduler 
tries the following options in order, aiming to minimize overhead:

\begin{enumerate}[label=\roman*)]
    \item \textbf{Reuse} an existing instance of the same function whose current 
    resource allocation already meets or slightly exceeds the request's demand, 
    thereby avoiding any scaling~operation.
    
    \item \textbf{In-place scaling} of a warm instance via restart-free vertical 
    scaling (Kubernetes Pod resize API) to accommodate the request, thus preserving 
    warm state.

    \item \textbf{Launch a new instance} (cold start) if no suitable warm instance 
    is available.
\end{enumerate}

If the node lacks sufficient idle resources for options ii) or iii), the scheduler 
evaluates pod eviction. It selects candidate instances according to a per-sandbox 
eviction priority:
\[
\text{Prio}_{\text{instance}} = \frac{\text{Prio}_{\text{function}}}{N_{\text{instances}}},
\]
where \(N_{\text{instances}}\) is the number of active instances belonging to 
the same function. Among instances of the same function, those with larger resource 
footprints are evicted first. This scheme encourages load spreading (by penalizing 
functions that already hold many instances) and promotes balanced resource sharing. 
Pod eviction is performed only if it can actually release enough resources to execute 
the pending request; otherwise, the scheduler leaves the system unchanged and waits 
for the next scheduling event.

\subsubsection{Priority Design}
\label{subsec:priority-design}

The scheduler assigns a dynamic priority to each function $F_i$ to balance three 
objectives: minimizing cold-start overhead, preventing request starvation, and 
maximizing the utility of in-place scaling. The priority is computed as a 
weighted sum of three factors:
\[
\text{Priority}(F_i) = \omega_1 \cdot \text{factor}_1 \;+\; \omega_2 \cdot \text{factor}_2 \;+\; \omega_3 \cdot \text{factor}_3,
\]

where the weights $\omega_1, \omega_2 > 0$ and $\omega_3 < 0$ are tunable 
parameters (set to $0.3$, $1.1$ and $0.8$ respectively in our implementation). 
The three factors are defined as follows:

\begin{itemize}
    \item \textbf{Cold-start cost factor} ($\text{factor}_1$).  
    Let $t_{\text{last}}$ be the request with the largest predicted resource demand 
    in $F_i$'s current queue, and let $C_{\text{cold}}(F_i)$ denote the estimated 
    cold-start cost of $F_i$ (\emph{i.e.}, the time overhead of launching a new 
    instance). Then
    \[
    \text{factor}_1 = \max\!\left(\frac{t_{\text{last}}^{\text{mem}}}{C_j^{\text{mem}}},\; \frac{t_{\text{last}}^{\text{cpu}}}{C_j^{\text{cpu}}}\right) \cdot C_{\text{cold}}(F_i),
    \]
    where $C_j^{\text{mem}}$ and $C_j^{\text{cpu}}$ are the memory and CPU 
    capacities of the worker node $N_j$ on which the scheduler is running. This 
    factor increases when the largest pending request occupies a large fraction of 
    the node's resources and the function itself is expensive to cold-start. It 
    encourages the scheduler to keep executing $F_i$'s requests consecutively, 
    thereby raising the chance of reusing a warm instance.

    \item \textbf{Starvation-avoidance factor} ($\text{factor}_2$).  
    Let $W_{\max}$ be the longest waiting time among all pending requests of $F_i$,
    and let $\overline{T}(F_i)$ be the average execution duration of $F_i$ requests. 
    The starvation factor is zero if no request has been waiting excessively; otherwise 
    it grows with the cumulative waiting time and the total work left in the~queue:
    \[
    \text{factor}_2 = 
    \begin{cases}
    0, & \text{if } W_{\max} < 3 \cdot \overline{T}(F_i),\\[4pt]
    \overline{T}(F_i) \cdot |Q_i| + W_{\max}, & \text{otherwise}.
    \end{cases}
    \]
    Here $|Q_i|$ is the total number of requests in $F_i$'s current queue. This 
    mechanism ensures that a function whose requests have been waiting too long 
    receives a priority boost, preventing indefinite starvation.

    \item \textbf{Scaling-efficiency factor} ($\text{factor}_3$).  
    Let $t_{\text{first}}$ and $t_{\text{last}}$ be the requests with the smallest 
    and largest predicted resource demands in $F_i$'s current queue, respectively. 
    Under the assumption that all requests of the same function share the same 
    CPU-to-memory ratio (see \S\ref{subsec:modeling}), the ratio can be computed 
    using either dimension; we use memory for concreteness:
    \[
    \text{factor}_3 = \frac{t_{\text{first}}^{\text{mem}}}{t_{\text{last}}^{\text{mem}}}.
    \]
    A large ratio (close to 1) indicates that the queue's resource-demand range is narrow; consequently, a current instance (if any) requires little or no additional scaling to process all requests in the current queue, resulting in low execution cost. A small ratio (i.e., a wide demand spread) implies that the current instance would need substantial or multiple scaling steps to process the entire queue, making it less beneficial to continue with the current instance.
\end{itemize}

Finally, to further promote instance reuse, the priority of any function that already possesses one or more warm instances is \textbf{doubled}. The combined priority is recomputed at every scheduling event, enabling the scheduler to adapt dynamically to changing workload patterns.
